# 確認的規則與程式不一致時

> **繁體中文** | [English](confirmed-rule-vs-code.en.md)

> 本頁跟著原始碼的 `main` 分支走，可能描述 changelog 還列在 `## Unreleased` 的行為。你的專案跑的是它 workflow bundle 裡的那一版 flow：`dflow/specs/shared/dflow-workflows/references/` 底下沒有 `confirmed-rule-vs-code.md`，就表示你的專案還沒有這一套記法——升級 CLI 之後跑一次 `dflow configure-agents` 就會有。

開發者確認了一條業務規則，程式卻沒有照著做，而這次決定先不修——例如規則是「資格要核准之後才釋出」，程式卻在送出時就釋出。文件如果只記程式現況，新功能會把 bug 當成規格繼承下去；如果只記規則，查現況的人會以為程式已經做到。Dflow 把兩者分開記：規則照確認的寫，程式實際怎麼做另外記成**偏離**，連到一列技術債；修好之後，由 `/dflow:finish-feature` 收尾時把偏離收掉。

這一頁說明各份文件的分工、什麼時候記、收尾怎麼收，以及這套做法管不到的地方。AI 實際照著做的程序在你專案的 workflow bundle 裡（`dflow/specs/shared/dflow-workflows/references/confirmed-rule-vs-code.md`），這一頁不重抄。想知道其中某條規定為什麼這樣定，問你的 AI 助手：它會在同一個目錄的 `flow-rationale-registry.md` 查 `R-CRVC-` 開頭的那幾條。

## 各份文件記什麼

| 文件 | 記什麼 |
|---|---|
| `rules.md` | 規則照確認的寫。最後一欄 `Known deviations`：有延後修的偏離時，連到記這個偏離的那一列技術債；沒有就是 `—`。 |
| `behavior.md` | Given/When/Then 情境只寫確認的規則。程式實際怎麼做，寫在那條規則標題下的一行 `> Known deviation:`：觀察到什麼、證據、技術債連結。你確認過「程式確實這樣做」、而且那個確認記在打得開的地方時，證據保留原本那段，後面接上誰、在哪裡確認的。 |
| `analysis.md` | 表格照實記程式怎麼做；轉移的 Guard 寫「應該由哪條規則決定它」，不寫程式裡的條件。條目引用了某條規則、程式卻沒照做時——不論引用寫在表格的一列，還是表格外的一句說明——條目旁邊加一行 `> Known deviation:`，指出違反的是哪條規則。 |
| 技術債（brownfield 是 `migration/tech-debt.md`，greenfield 是 `architecture/tech-debt.md`） | 一個偏離一列，名稱像 `Qualification BR-007: release timing`：哪條規則、確認的規則摘要、程式現況、規則與程式各自的證據、為什麼延後。 |
| 這次工作的 spec | flow 進行中確認並延後的偏離，在 spec 標題底下記一行 `> Deferred deviation:`。刪掉一條帶著偏離的規則時，在 REMOVED 條目底下記一行 `**Recorded deviation**:`，收尾才找得到它。 |

兩條界線：

- **`—` 只表示沒有用這個格式記下偏離，從來不表示有人查過程式。** 沒有偏離紀錄，不代表程式照規則做。
- **偏離不是規則，也不是合法的 edge case。** 它不寫進規則文字、不進 feature 的 BR Snapshot，也不拿 EC 編號。

## 什麼時候會記

- 只在**你確認了規則、也決定延後修**的時候。AI 不會因為讀了程式就宣稱某條規則已經確認；確認不了的，照舊記成 `draft` 與待決問題。
- 只在當下的工作本來就能改那個 context 的文件時：宣告了那個 bounded context 的變更，或 flow 允許的觀察紀錄（brownfield 是 baseline 盤點，greenfield 是 `/dflow:modify-existing` 的觀察紀錄）。T3、或沒有宣告 bounded context 的變更不寫——AI 會告訴你它看到什麼、還有什麼沒記。
- flow 進行中確認的，先在 spec 記那一行延後紀錄；`rules.md`、`behavior.md` 與技術債，在那個 flow 寫這些文件的那一步補上。`/dflow:new-phase` 不寫這些文件，所以留到收尾補。
- 驗證與 PR review 碰到帶著延後紀錄的 spec：把那一個偏離當成已知的例外，並引用那一列技術債。但這份 spec 自己要加、要改或要修那個行為時——它的 Delta、它新加的規則、family (e) 要修的缺陷，或修那個偏離的任務——就不算例外：延後紀錄寫下之後不再改，這份 spec 後來決定修它，照樣要修到。其他沒做到的地方照樣不過。
- 用舊方式記的偏離（例如寫成 edge case）不會自動轉換：之後的工作碰到那條規則、你也確認它是延後修的缺陷時，AI 才改成這個記法。原本就有的那一列技術債直接改成記這個偏離，名稱沿用原來的。你若說那個情況其實沒有確認過的規則，它就不是偏離：AI 把程式現況改記成不帶規則編號的觀察，還沒定的照待決問題處理。

## 修好之後誰收掉

偏離只在 `/dflow:finish-feature` 收尾的 Step 3 收掉，其他地方都不收：情境改寫了、spec 有 BR Delta、spec 標成 `completed`，都不算修好的證據。

- **有訊號才收。** host（掛載這次變更的規格紀錄目錄，不是程式目錄）的 spec 指名了帶偏離的規則、連到一列技術債，或帶著延後紀錄，Step 3 才讀收尾程序；都沒有，就只印一行 `Debt reconciliation: no signal`。
- **要有證據。** AI 打開這個 feature 的測試結果與實作位置，對照紀錄寫的條件。資料不夠、同一條規則有好幾個入口，或範圍不清楚時，它會問你：「這個 feature 修好了哪幾個入口、還留下哪幾個偏離？」
- **修好的**：`rules.md` 那一格改回 `—`，指向它的每一行偏離紀錄都拿掉（包括其他 context 的 `analysis.md`），技術債設成 `done`，並在那一列記下是哪一份 spec 修好的。
- **沒修好、或只修了一部分的**：保留，更新還剩下的範圍與證據。收尾同步之後，AI 會確認它在 `rules.md` 那一格與 `behavior.md` 那一行都還在，缺的補上。延後之後，這個 host 沒有任何修它的工作時，延後紀錄本身就是沒修的證據：保留，不再問你。
- **規則刪掉或改掉、所以不再適用的**：照原樣結案，記成 `Closed by rule change`，不記成測試過的修復。
- 這次還清、而且 spec 有連到的一般技術債，也在這一步設成 `done`。
- Step 3 最後印出 `Resolved deviations: …; debt done: …; retained: …`。

## 圖只照表格畫

`dflow render` 照 `analysis.md` 的表格畫狀態圖與流程圖：Trigger 是觀察到的動作，Guard 是決定它的規則。圖不標出哪一條轉移違反規則——偏離寫在圖旁邊的文字裡。只看圖的人（例如收到一張截圖），會把畫出來的每一條轉移都當成允許的。要判斷一條轉移合不合規則，看完整的頁面。

## 升級既有文件

兩軌 `rules.md`、`behavior.md`、`tech-debt.md`、`lightweight-spec.md` 的範本都升了形狀號碼，`dflow doctor` 會對既有文件報舊形狀。`rules.md` 的新欄與 `behavior.md` 的 Purpose 說明這兩項，doctor 會印出它們自己的遷移句：既有的列填 `—`（不是 `{TBD}`），Purpose 換成範本的新句。為什麼這樣做，見[升級既有 Dflow 專案](upgrading.md)裡的「自帶遷移句的變更」。

## 做了之後仍然存在的風險

以下每一項都想過，也刻意不另加防線：要防住，每一次執行（或每一個採用者）要付的代價比它防的錯還大，或者那本來就是要人判斷的事。每一項都寫明由誰承擔、什麼情況下會重新考慮。

- **只看圖，以為畫出來的轉移都是允許的。** 圖照表格畫：Trigger 是觀察到的動作，Guard 是決定它的規則；偏離寫在旁邊的文字裡，CLI 不做規則推理。*誰承擔*：分享與閱讀圖的人。*會重新考慮的情況*：有真實的誤判回報，或需要單獨匯出圖的時候。
- **升級後 guide 沒有刷新，或 AI 只讀了舊範本，沒讀到這套記法。** 升級與人工比對保證不了每一個工具都讀到新的指示。*誰承擔*：採用者。*會重新考慮的情況*：升級之後仍然一再出現不同的記法。
- **同一個偏離在幾份文件之間記得不一致，或有人沒走 `/dflow:finish-feature` 就收尾。** 沒有跨文件比對語意的檢查；收尾 Step 3 與 review 照證據比對。*誰承擔*：feature 的負責人與 reviewer。*會重新考慮的情況*：出現重複漏清或誤清的實際案例時，再考慮機械輔助。
- **spec 沒有指名相關的規則、也沒有連到技術債，收尾就沒有訊號。** 訊號只看 spec；沒有訊號不代表程式沒有缺陷。*誰承擔*：spec 的作者與 reviewer。*會重新考慮的情況*：照標準寫法仍然常常漏掉。
- **這次工作還清了一筆一般技術債，但沒有任何 spec 連到它。** 收尾不掃全部技術債，那一列維持 `open`，要有人自己設成 `done`。*誰承擔*：開發者與 reviewer。*會重新考慮的情況*：常見到值得讓每一次收尾都付掃描的成本。
- **同一個 feature 先延後、後來修好了，但修的工作沒寫進收尾讀的 spec**（沒指名那條規則，也沒連到那一列技術債）。延後紀錄在收尾是證據：找不到修它的工作，就保留、不問你。錯的方向是該清的紀錄留著，不是沒修的被清掉——清除仍然要先過證據。*誰承擔*：開發者與 reviewer——修好時在 spec 指名那條規則或連到那一列技術債，或收尾時直接告訴 AI。*會重新考慮的情況*：這種漏記常見到值得每次收尾都問。
- **程式修了，但資料還沒回補，或其他入口仍然錯。** 一次修復只是候選，不是完成的證明；只修了一部分就保留紀錄，不能靠一個測試把整列結掉。*誰承擔*：開發者對修復範圍的確認。*會重新考慮的情況*：資料修復與程式修復一再被混為一談。
- **收尾之前已經修好，偏離紀錄卻還在。** 紀錄寫著觀察的日期，看得出那是什麼時候的觀察；正式收掉只在收尾 Step 3。*誰承擔*：feature 進行中讀文件的人。*會重新考慮的情況*：跨好幾個 phase 長期造成誤用時，先量測，再評估怎麼呈現，不悄悄改收掉的時點。
- **`/dflow:new-phase` 途中確認並延後的偏離，收尾之前只記在 phase spec 裡**，`rules.md` 與 `behavior.md` 還看不到。new-phase 的寫入範圍不為它改；驗證與 review 認 spec 的那一行，收尾 Step 3 依它補齊。*誰承擔*：收尾之前只讀 `rules.md`／`behavior.md` 的人。*會重新考慮的情況*：多個 phase 拖很久才收尾，而且因此造成誤用。
- **升級前用舊方式記的偏離（例如寫成 edge case），在 `Known deviations` 顯示 `—`。** 既有的列一律填 `—`，`—` 的界線寫在欄位註解與這一頁。*誰承擔*：只讀 `rules.md` 一列的人；之後的工作碰到那條規則時轉換。*會重新考慮的情況*：有採用者回報因此誤讀，再考慮改填一個待確認的值，或提供一次性盤點的做法。
- **brownfield 的 baseline 盤點掛在有 phase 的 feature 上，確認的內容會改變那個 feature 的 BR Snapshot 帶著的某條規則的意思。** 這次不改那條規則——否則收尾同步會拿 Snapshot 上的舊文字，把剛確認的規則寫回去。確認的內容記在 `rules.md` 的 `## Open Questions` 與 host 的 Goals & Scope，技術債照寫；`rules.md` 那一格與就地的偏離行，要等之後改了那條規則才補，在那之前它們只能指向還沒改的舊文字。*誰承擔*：之後改這條規則的變更。*會重新考慮的情況*：出現可重現、長期卡住的情境。
- **brownfield 的 baseline 盤點只在 `rules.md` 一列的 BR-ID、Rule summary、Behavior anchor、Status 改了時更新 `Last updated`，專案自己加的欄改了不動。** 專案在自己加的欄放規則內容時，一般 flow 把同一個改動記成修改、日期會動，baseline 盤點不會，兩邊不一致。不防的理由：要 AI 每一次判斷自己加的欄算不算規則內容，同一種改動會判得不一樣，所以只看範本的欄。*誰承擔*：在自己加的欄放規則內容的專案，與靠這個日期判斷規則新舊的人。*會重新考慮的情況*：有採用者回報因此誤判。
- **AI 把「確認了規則」或「決定延後」，當成「確認了程式現況」接在證據後面。** 三種確認常在同一次 baseline 盤點的確認裡接連發生；分辨它們要看你確認的是什麼，現有的機械檢查只比對字樣、證明不了這一點，所以這個判斷留給執行的 AI 與 review。*誰承擔*：讀偏離紀錄的人。*會重新考慮的情況*：實際看到這樣誤寫。
- **舊的 edge case 其實是缺陷，AI 卻把它當成合法情境。** 不做全自動轉換；碰到那條規則時由你判斷。*誰承擔*：採用者。*會重新考慮的情況*：有需要一次性盤點的回報時，再提供操作說明。
- **規則改名之後，技術債的名稱還顯示舊的 BR-ID。** 名稱建立之後就不改——spec 裡的延後紀錄與連結都靠它找到那一列；現在追蹤的是哪一條規則，看那一列的 `BR:`。*誰承擔*：只看名稱的人。*會重新考慮的情況*：有人因此找錯規則。
- **改過名或搬離 flow 建立它的路徑、又沒有讀得到的形狀標記的 `rules.md`／`behavior.md`，拿不到 doctor 的遷移句。** 照通用的補形狀做法，可能把新欄填成 `{TBD}`、留下舊的 Purpose。doctor 只替認得出範本的文件印遷移句：有標記的看標記，沒有或讀不到標記的看路徑；這些文件也不在 Dflow 的 flow 裡，收尾找不到它們。*誰承擔*：處理這些文件的你與 AI——遷移句說的就是上面「升級既有文件」那兩件事。*會重新考慮的情況*：改名或搬走的文件常見，而且出現照通用做法改錯的回報。

**檢查通過不代表偏離修好了。** `/dflow:verify` 的 BR 與 anchor 對照通過、`dflow doctor` 的形狀檢查通過、`dflow check-closeout` 通過，都不證明偏離已經修好；那由收尾 Step 3 的證據、AI 與你判斷。
