# `analysis.md` 的已知限制

> **繁體中文** | [English](analysis-limitations.en.md)

> 本頁跟著原始碼的 `main` 分支走，可能描述 changelog 還列在 `## Unreleased` 的行為。你的專案用的是它 workflow bundle 裡的那一版範本：`dflow/specs/shared/dflow-workflows/templates/analysis.md` 的 `## Lifecycles` 註解沒有提到 `[*]`，就表示你的專案還沒有生命週期的新寫法——升級 CLI 之後跑一次 `dflow configure-agents` 就會有。

`analysis.md` 的寫法與 `dflow render` 畫的圖，有幾處是我們知道、但決定不防的。這一頁逐項寫出來：會出什麼錯、為什麼不防、誰承擔、什麼條件下會重新考慮。
決定不防，通常是因為要防就得讓機器去判讀它判不準的內容，或者為了少數情況讓每一份文件多付成本。

## 生命週期：新建與刪除（`[*]`）、沒有轉移的值、寫不出原樣的值

生命週期的轉移表裡，From 寫 `[*]` 表示那一步建立了這筆資料，To 寫 `[*]` 表示那一步把它刪掉；`[*]` 不是值，不列進狀態表。
沒有任何轉移寫到的值，`dflow render` 列在圖下、不畫成方框；這張值清單從哪裡來，寫在兩張表後面的一行 `Evidence:`。
空字串、全是空白、沒有值這類寫不出原樣的值，在 State 取一個名字，由那一行 `Evidence:` 說明每個名字代表什麼。

1. **名字由各專案自己取，跨專案不統一。** 同樣是「沒有值」，有的專案寫「（未設定）」，有的寫「（無）」。
   - 為什麼不防：同一份文件裡不會混淆，表後的 `Evidence:` 那一行寫明每個名字代表什麼；定一套固定記號，又會和真的存了那幾個字的值撞在一起。
   - 承擔：跨專案讀文件的人。
   - 重看：有人回報因此讀錯時。
2. **To 的 `[*]` 可能被誤寫成「終點狀態」。** 熟悉 Mermaid、PlantUML 的 AI 或作者，可能替「已結案」這類停在那裡的狀態加一列到 `[*]`，表上就多了一個沒有發生過的刪除。
   - 為什麼不防：系統有沒有真的刪除，機器判斷不了；範本那一句（停在某個值不再變的、軟刪除，都是普通狀態）與圖例是唯一的提醒。
   - 承擔：寫的人與審查的人。
   - 重看：實際出現時。
3. **可以從很多個狀態刪除時，圖可能畫不出來。** 一個狀態一列，從大約 6 個狀態都能刪除起，箭頭需要的分道超過上限，`dflow render` 改印一行說明、不畫圖。表格照樣完整。
   - 為什麼不防：為了畫得出來而少寫幾列，正是這套寫法要避免的錯。
   - 承擔：讀圖的人（改看表格）。
   - 重看：這種生命週期變常見時（例如把指向終點的箭頭改排到左側）。
4. **`dflow render` 分不出一個值為什麼沒有轉移。** 沒有人查過它的轉移、只出現在舊資料裡、程式寫得出來卻走不到，都一樣列在圖下；原因要讀表後的 `Evidence:` 那一行，而 render 不檢查那一行寫了沒有。
   - 為什麼不防：原因是散文，機器判不準；判不準的檢查只會製造提示。
   - 承擔：讀的人與審查的人。
   - 重看：常有人漏寫那一行時。
5. **既有文件不會被 `dflow doctor` 點名。** 寫在表下的新建步驟、為了畫圖從狀態表拿掉的值，`dflow doctor` 都不會提示——它只比對範本的形狀號碼。只有升級時的遷移說明會提醒一次。
   - 為什麼不防：要讀表下的散文與值清單的內容才判斷得出。
   - 承擔：採用者。
   - 重看：同第 4 項。
6. **舊版 CLI 讀到 `[*]`。** 從 `0.15.0` 有畫圖起、到 `0.16.4` 的 CLI，看到 From 或 To 寫 `[*]` 會印「（[*]）不在狀態表裡」、不畫圖；放回狀態表的值會照舊算進狀態數的上限，可能因此改印說明。一般情況不會畫錯，只是沒有圖。
   **例外**：文件另外定義了 `[*]:` 這個連結、`[*]` 又沒加反引號、狀態表剛好有 `*` 這個值時，舊版會把那一列畫成一條普通的轉移。
   - 為什麼不防：舊版已經發出去了。
   - 承擔：還沒升級 CLI 的人。
   - 重看：不需要。
7. **名字代表什麼，只寫在 `Evidence:` 那一行。** 漏寫時，讀者看到「（未設定）」得自己猜它是 NULL 還是空字串；`dflow render` 不檢查那一行。
   - 為什麼不防：同第 4 項。
   - 承擔：寫的人與審查的人。
   - 重看：常有人漏寫時。
8. **加上起點、終點之後，原本剛好畫得出來的圖可能畫不出來。** 起點、終點各至少佔 64 的高度；今天剛好在 960 以內的圖，加了之後改印說明，表格不受影響。
   例如 10 個狀態、其中一條轉移有一行 Guard 與 `inferred` 標籤的生命週期，今天高 898；加上起點變成 962，超過上限。
   - 為什麼不防：記號要有位置。
   - 承擔：讀圖的人（改看表格）。
   - 重看：這種情況變常見時（例如把記號畫在第一個、最後一個狀態旁邊，不另佔一段）。
9. **舊文件用連結 `[*]` 指向一個叫 `*` 的值。** 文件另外定義了 `[*]:`、From 或 To 寫了沒加反引號的 `[*]` 時，`dflow render` 判斷不了作者要的是新建／刪除、還是 `*` 這個值，所以不畫圖，印一行說明請作者改寫：新建、刪除寫成加反引號的 `[*]`，那個值寫成加反引號的 `*`。不會畫錯。
   - 為什麼不防：不論猜哪一種，都會在另一種文件畫錯。
   - 承擔：那份文件的作者（極少見）。
   - 重看：不需要。
10. **State、From、To 格寫了 HTML、圖片或字元參照。** 這幾種寫法在頁面上顯示什麼，由瀏覽器決定：HTML 可以把字藏起來（例如 `<span hidden>`），`&amp;`、`&#91;` 這類參照會換成另一個字。`dflow render` 不去模擬，所以這三種格子裡只要有 `<br>` 以外的 HTML、圖片，或反引號以外的字元參照，就不畫那張圖，印一行說明請作者照範本把值寫在反引號裡（例如 `` `R&D` ``）。前面的格子或段落打開了 `<pre>`、`<code>`、`<kbd>`、`<script>` 還沒關上時也一樣：這幾個標籤後面的文字會原樣交給頁面。不會畫錯。範本的寫法（值放在反引號裡）、一般文字與粗體不受影響，Trigger、Guard 這類說明格也照舊。
   但說明格裡的 HTML 不在這條規則裡：少數標籤沒關上時會吞掉後面的格子（例如 `<textarea>`、`<style>`、`<template>`、HTML 註解），頁面上那幾格會不見或變成亂碼，圖仍照 Markdown 寫的值畫。
   - 為什麼不防：要判得準，就得照瀏覽器的規則解讀所有 HTML 與參照；只認其中幾種，總會有沒想到的寫法被讀錯，而讀錯就是畫錯圖。說明格的 HTML 若也一律不畫，代價落在說明格用了 HTML 的每一份文件，而那種吞掉格子的情況，頁面上的表格本身就壞了。
   - 承擔：用了這些寫法的文件作者（極少見）；說明格那一種，由對照圖與表格的讀者承擔。
   - 重看：有人回報常用的寫法被擋下，或說明格的 HTML 讓圖與表格對不起來時。

## Function / Role Index：各角色能做的事（`Role-specific actions`）

1. **用關鍵字找動作，命中的是文字，不是權限。** 命中的那一行寫的可能是限制（例如「鎖定後不能改」），不是能做的事。
   - 為什麼不防：任何寫法都會有，讀那一行就分得出來。
   - 承擔：讀的人與 AI。
   - 重看：常需要回答「誰能做某個動作」、或要從這張表產出授權測試時，考慮另加一張一列一個動作的權限表。
2. **沒有機器檢查。** `dflow doctor` 與 `dflow render` 不驗每行開頭的角色在 Roles 裡、一行只有一個動作或一個引用、寫 `—` 的列真的查過。
   - 為什麼不防：都要讀內容才判得出，判不準的檢查只會製造提示。
   - 承擔：寫的人與審查的人。
   - 重看：實際出現這類錯而沒有人發現時。
3. **這一欄是授權分析的輸入，不是授權政策。** 它只寫不是每個角色都有的動作，可能只寫規則的引用，記的也可能是從程式觀察到、沒有確認過的行為。改寫系統時，仍要解開引用、把動作與條件分開、補回每個角色都能做的事、判斷觀察到的是不是確認過的規則。
   - 為什麼不防：這張表的工作是索引，不是授權規格。
   - 承擔：改寫系統的人。
   - 重看：同第 1 項。
4. **Bounded Context 的 `—` 是「目前記下的 context 都不合適」**，不是「永遠不屬於任何 context」；本來就不屬於業務 context 的（登入、個人設定之類），由那一題的答案說明。
   - 為什麼不防：兩種情況要分開記，就得多一種記號。
   - 承擔：讀的人。
   - 重看：需要分開時。
5. **`dflow doctor` 不看格子的內容。** 它只比形狀號碼，所以升級後既有的 Bounded Context 空格不會被點名，遷移時有沒有照遷移說明填也判斷不了。
   - 為什麼不防：同第 2 項。
   - 承擔：採用者，下次碰到那一列時照新規則寫。
   - 重看：同第 2 項。
6. **升級前寫的多角色列是「還沒查」。** 遷移只補欄、不查；在有人查過之前，那些列的空格不代表任何事。
   - 為什麼不防：查要讀程式或問人，不是機械的。
   - 承擔：讀的人與改寫系統的人（改寫前要查）。
   - 重看：升級後很少有人回頭補查時，考慮讓 `dflow doctor` 提示還沒查的多角色列。
